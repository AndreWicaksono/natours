## Executive Summary

The implemented modules are structurally sound and largely correct. There are **9 confirmed bugs / gaps** ranging from critical to low, plus **6 industry-best-practice gaps** worth addressing. None block the happy path for a single user in isolation, but several create correctness failures under load or for edge scenarios explicitly described in the requirements.

## 🔴 Critical / High Priority Findings

### BUG-1 — `BookingStatusService` ONGOING → COMPLETED logic is broken
**File**: [`booking-status.service.ts`](file:///home/andre/Candradimuka/natours/apps/api/src/bookings/booking-status.service.ts) L31–43  
**Problem**: The cron that transitions `ONGOING → COMPLETED` has a **comment admitting it doesn't work**:
```ts
// Note: You'll need to calculate end date = startDate + durationDays
// This requires a more complex query or a computed field
```
The current `updateMany` where-clause only checks `durationDays > 0` — it never filters by whether the tour end date has actually passed. **Every `ONGOING` booking (with a tour that has any duration) is set to `COMPLETED` every day the cron runs**, regardless of whether the tour has ended.

**Impact**: Violates the Core User Flow (Step 8: `ONGOING → COMPLETED` after tour ends) and blocks all negative-flow scenarios where a tour is still running.

**Fix**: Raw SQL, subquery, or Prisma's `$queryRaw` to compare `startDate + durationDays * interval '1 day' < NOW()`:
```ts
await this.prisma.$queryRaw`
  UPDATE tour.bookings
  SET status = 'COMPLETED'
  WHERE status = 'ONGOING'
    AND tour_schedule_id IN (
      SELECT ts.id
      FROM tour.tour_schedules ts
      JOIN tour.tours t ON t.id = ts.tour_id
      WHERE ts.start_date + (t.duration_days || ' days')::interval < NOW()
    )
`;
```

### BUG-2 — `BookingStatusService` CONFIRMED → NO_SHOW uses wrong boundary (`today` is midnight local, compared with UTC `startDate`)
**File**: [`booking-status.service.ts`](file:///home/andre/Candradimuka/natours/apps/api/src/bookings/booking-status.service.ts) L17  
**Problem**:
```ts
const today = new Date(now.getFullYear(), now.getMonth(), now.getDate()); // LOCAL time midnight
```
`startDate` in the database is stored as `timestamptz` (UTC-based). Comparing a local-time midnight against a UTC timestamp can cause NO_SHOW transitions to fire a day early or late depending on server timezone offset. The `startDate` field in `TourSchedule` is set via Prisma from JavaScript `Date` objects, so it's UTC-anchored.

**Fix**: Use UTC midnight consistently:
```ts
const today = new Date(Date.UTC(now.getUTCFullYear(), now.getUTCMonth(), now.getUTCDate()));
```

### BUG-3 — `ExpirationService` calls `paymentsService.updatePaymentStatus()` inside a Prisma transaction, which may silently fail
**File**: [`expiration.service.ts`](file:///home/andre/Candradimuka/natours/apps/api/src/bookings/expiration.service.ts) L36–58  
**Problem**: `this.paymentsService.updatePaymentStatus()` internally calls `this.prisma.payment.updateMany()`. Calling a **separate Prisma client operation** inside a `prisma.$transaction()` callback does **not** enlist it in the same transaction — it runs on the pool's regular connection. If the outer transaction rolls back, payment status has already been mutated.

**Fix**: Either (a) pass the transaction client `tx` through to the payment update call, or (b) move the payment status update outside the transaction block as a post-commit step.

### BUG-4 — `ToursService.findOne()` applies partner isolation to CUSTOMER role, blocking customers from viewing individual tours
**File**: [`tours.service.ts`](file:///home/andre/Candradimuka/natours/apps/api/src/tours/tours.service.ts) L163–168  
**Problem**:
```ts
if (user.role !== AppRole.ADMIN) {
  if (tour.partnerId !== user.partnerId) {
    throw new ForbiddenException('You do not have access to this tour.');
  }
}
```
A `CUSTOMER` user has `partnerId = null`. A tour with any `partnerId` will always fail this check (`null !== somePartnerId` → `true` → 403). **Customers can never view a single tour's detail page**, even for `LIVE` tours.

**Fix**: Only apply partner isolation to `PARTNER_ADMIN`/`GUIDE`/`LEAD_GUIDE` roles. For `CUSTOMER`, only check that the tour is `LIVE` and not deleted (which `findFirst` with `isDeleted: false` already ensures):
```ts
if (user.role === AppRole.PARTNER_ADMIN || user.role === AppRole.GUIDE || user.role === AppRole.LEAD_GUIDE) {
  if (tour.partnerId !== user.partnerId) {
    throw new ForbiddenException('You do not have access to this tour.');
  }
} else if (user.role === AppRole.CUSTOMER) {
  if (tour.status !== TourStatus.LIVE) {
    throw new NotFoundException(`Tour with ID ${id} not found.`);
  }
}
```

### BUG-5 — `cancelBooking` marks payment as `FAILED` for a booking that was already paid (CONFIRMED status)
**File**: [`bookings.service.ts`](file:///home/andre/Candradimuka/natours/apps/api/src/bookings/bookings.service.ts) L489–493  
**Problem**: A user cancelling a `CONFIRMED` booking (payment already `SUCCEEDED`) gets their payment record set to `FAILED`. This conflates "cancelled booking" with "payment failure" — they are different states. The correct terminal payment status for a user-initiated cancellation after payment is `REFUNDED` (even if the Stripe refund hasn't been issued yet, the intent is different).

**Fix**: Check current booking status before choosing payment status:
```ts
const paymentStatus = booking.status === BookingStatus.PENDING
  ? PaymentStatus.FAILED
  : PaymentStatus.REFUNDED; // CONFIRMED → CANCELLED implies customer is owed a refund
await this.paymentsService.updatePaymentStatus(bookingId, paymentStatus);
```
Note: `PaymentStatus` enum may need `REFUNDED` added if it doesn't already exist.

## 🟡 Medium Priority Findings

### BUG-6 — `BookingsController.confirm()` is a manual endpoint restricted to ADMIN/PARTNER_ADMIN, but confirmation is supposed to be webhook-driven only
**File**: [`bookings.controller.ts`](file:///home/andre/Candradimuka/natours/apps/api/src/bookings/bookings.controller.ts) L50–58  
**Problem**: `PATCH /bookings/:id/confirm` exists and calls `bookingsService.confirmBooking(id)` directly, bypassing payment verification entirely. An `ADMIN` or `PARTNER_ADMIN` can confirm any booking without any Stripe payment event occurring. Per the README's Detailed Flow (Step 5), confirmation must only happen via the `checkout.session.completed` webhook.

**Risk**: Bookings could be "confirmed" with no payment attached, leading to seats reserved permanently and no `PlatformTransfer` record created.

**Fix**: Remove this controller endpoint entirely. `confirmBooking()` is already called correctly by the webhook handler.

### BUG-7 — `AvailabilityService.getAvailableDates()` uses only the **first** availability rule (`findFirst`), silently ignoring all others
**File**: [`availability.service.ts`](file:///home/andre/Candradimuka/natours/apps/api/src/tours/availability.service.ts) L11–13  
**Problem**:
```ts
const rule = await this.prisma.availabilityRule.findFirst({ where: { tourId } });
```
A tour may have multiple availability rules (e.g., "Mondays + Wednesdays" and "Saturday + Sunday" as two separate rules). `findFirst` returns only one. The availability calendar will appear incomplete, confusing customers.

**Fix**: Use `findMany` and aggregate all matching slots across all rules:
```ts
const rules = await this.prisma.availabilityRule.findMany({ where: { tourId } });
// Then iterate over all rules for each day in the month
```

### BUG-8 — `resumePayment` creates a new Stripe session without `application_fee_amount`, losing platform commission
**File**: [`bookings.service.ts`](file:///home/andre/Candradimuka/natours/apps/api/src/bookings/bookings.service.ts) L375–406  
**Problem**: The `resumePayment` Stripe session creation omits `application_fee_amount` in `payment_intent_data`. The `createBookingWithCheckout` flow correctly applies the platform fee, but if a customer uses `POST /bookings/:id/resume-payment`, the platform earns zero commission on that payment.

**Fix**: Re-calculate and include `application_fee_amount` in the resume payment session, matching the original booking's fee calculation.

### BUG-9 — `cancelBookingByAdmin` does not cancel `ONGOING` bookings (partial status guard)
**File**: [`bookings.service.ts`](file:///home/andre/Candradimuka/natours/apps/api/src/bookings/bookings.service.ts) L508–516  
**Problem**:
```ts
if (
  booking.status === BookingStatus.CANCELLED ||
  booking.status === BookingStatus.EXPIRED
) {
  // skip
  return;
}
```
This correctly skips already-terminal bookings, but it will also attempt to cancel `ONGOING` and `COMPLETED` bookings via Stripe refund webhooks. If Stripe issues a refund after a tour is already in progress, the booking status reverts to `CANCELLED` incorrectly. The guard should also skip `COMPLETED`/`NO_SHOW` terminal states.

**Fix**:
```ts
const terminalStatuses = [
  BookingStatus.CANCELLED,
  BookingStatus.EXPIRED,
  BookingStatus.COMPLETED,
  BookingStatus.NO_SHOW,
];
if (terminalStatuses.includes(booking.status)) {
  this.logger.warn(`Booking ${bookingId} already in terminal state ${booking.status}, skipping.`);
  return;
}
```

## 🟢 Industry Best-Practice Gaps

### BP-1 — `console.log` / `console.error` used in Stripe webhook controller instead of NestJS Logger
**File**: [`stripe-webhook.controller.ts`](file:///home/andre/Candradimuka/natours/apps/api/src/payments/webhooks/stripe-webhook.controller.ts) — multiple lines  
**Problem**: Raw `console.log`/`console.error` bypasses NestJS's structured logging. In production, structured logs (with timestamps, correlation IDs, severity levels) are essential for debugging webhook failures.  
**Fix**: Replace with `private readonly logger = new Logger(StripeWebhookController.name)` and use `logger.log()`, `logger.error()`, `logger.warn()`.

---

### BP-2 — No idempotency check on webhook processing (Stripe may deliver events more than once)
**File**: [`stripe-webhook.controller.ts`](file:///home/andre/Candradimuka/natours/apps/api/src/payments/webhooks/stripe-webhook.controller.ts)  
**Problem**: Stripe guarantees *at-least-once* delivery. The schema already has a `billing.stripe_webhook_events` table for idempotency tracking, but the webhook controller never uses it. A `checkout.session.completed` delivered twice would create two `PlatformTransfer` records for the same booking.  
**Fix**: Before processing any event, check/insert into `stripe_webhook_events` using `event.id`. If already present, return `200` immediately. Use an upsert or unique constraint on `event_id`.

### BP-3 — `JwtAuthGuard` still imported (but unused) in `bookings.controller.ts` and `partners.controller.ts`
**Files**: [`bookings.controller.ts`](file:///home/andre/Candradimuka/natours/apps/api/src/bookings/bookings.controller.ts) L16, [`partners.controller.ts`](file:///home/andre/Candradimuka/natours/apps/api/src/partners/partners.controller.ts) L14  
**Problem**: Per the Oct 4 commit that cleaned up redundant guard usage, `JwtAuthGuard` imports were left in both files despite not being used. This is misleading for anyone reading the code — the documented pattern says `@UseGuards(RolesGuard)` only.  
**Fix**: Remove the unused `import { JwtAuthGuard } from '../auth/jwt-auth.guard'` line from both files. Also remove the unused import from `reviews.controller.ts` L17.

---

### BP-4 — `test-expire` endpoint is `@Public()` in the same controller as production booking routes
**File**: [`bookings.controller.ts`](file:///home/andre/Candradimuka/natours/apps/api/src/bookings/bookings.controller.ts) L86–91  
**Problem**: This endpoint is documented as "keep for testing, remove in production" in `STATUS.md` Caveats. A public endpoint that triggers the expiration cron on demand represents a DoS vector (anyone can spam seat releases). Even in development it's a footgun.  
**Fix**: Gate it with `NODE_ENV !== 'production'` check in the handler body, or move it to a separate `DevController` that's only registered when `ConfigService.get('NODE_ENV') === 'development'`.

### BP-5 — `PartnersController` returns plain `{ error: 'Partner not found.' }` objects instead of throwing `NotFoundException`
**File**: [`partners.controller.ts`](file:///home/andre/Candradimuka/natours/apps/api/src/partners/partners.controller.ts) L40–42, L81–83  
**Problem**: Controllers should throw NestJS HTTP exceptions, not return error objects. Returning `{ error: '...' }` with a `200 OK` status is incorrect REST behavior and will confuse clients.  
**Fix**:
```ts
if (!partner) {
  throw new NotFoundException('Partner not found.');
}
```

### BP-6 — `SITE_URL` env variable used in `BookingsService` but documented as `APP_URL` in `README.md`
**File**: [`bookings.service.ts`](file:///home/andre/Candradimuka/natours/apps/api/src/bookings/bookings.service.ts) L287–288, [`partners-connect.service.ts`](file:///home/andre/Candradimuka/natours/apps/api/src/partners/partners-connect.service.ts) L87–88  
**Problem**: `README.md` → "Environment Variables" documents `APP_URL="http://localhost:3000"`. The code reads `this.configService.get('SITE_URL')`. This mismatch means Stripe success/cancel redirect URLs and the partner onboarding return URLs will be `undefined` in environments that only define `APP_URL`.  
**Fix**: Standardize to one name. The `README.md` documents `APP_URL` — update the code to use `APP_URL`, or update the README to use `SITE_URL`.
