## OI-1: Seat overbooking

**Where**: `bookings/bookings.service.ts`, `createBookingWithCheckout` (the seat-availability check and the booking transaction)
**Severity**: High

**What the code did**: it read `schedule.seatsAvailable`, compared it with the requested seats, and only later, inside a transaction, ran an unconditional `decrement`. Nothing protected the count between the read and the write.

**Scenario**: one seat is left. Customers A and B both read `seatsAvailable = 1` and both pass the check. A's transaction decrements to 0; B's decrements to -1. Both receive a checkout URL and both can pay for a seat that does not exist.

**Why the transaction did not help**: a transaction makes the writes inside it atomic with each other. It does not make the earlier read part of it. The check and the decrement had to become a single conditional statement. The 08-10-2026 audit listed this as "Confirmed Correct: no TOCTOU race on seats", which was wrong.

**Fix**: the seats are claimed with one conditional update, `updateMany({ where: { id, seatsAvailable: { gte: n } }, data: { seatsAvailable: { decrement: n } } })`. If another request took the seats first, `count` is 0 and the booking is rejected with "Not enough seats available." The earlier check stays as a friendly pre-check only.

**Not done (optional hardening)**: a database `CHECK (seats_available >= 0)` constraint would make a negative count impossible even if application code regresses.

## OI-2: A customer can pay for a booking that already expired

**Where**: `bookings.service.ts` (`createBookingWithCheckout`, `confirmBooking`, `expireBooking`), `expiration.service.ts`, `payments/webhooks/stripe-webhook.controller.ts` (`checkout.session.completed`)
**Severity**: Critical, because it takes a customer's money for something they do not get.

**What the code did**: three facts combined.
1. The seat hold was `expiresAt = now + 15 minutes`.
2. The Stripe Checkout Session was created without `expires_at`, so Stripe's default of **24 hours** applied.
3. `confirmBooking` silently returned when the booking was not `PENDING`, and the webhook carried on regardless: it marked the payment `SUCCEEDED` and created a `PlatformTransfer`.

**Scenario**: a customer opens the checkout page, gets distracted, and pays at minute 20. The cron has already expired the booking and released its seats, and someone else may have booked them. Stripe charges the card and sends `checkout.session.completed`. `confirmBooking` ignores the event, but the webhook records a successful payment and a partner payout for a booking that does not exist. The customer has paid and has no tour.

**A second, smaller race in the same area**: the expiration cron read its list of expired bookings outside its transaction and then updated each one unconditionally. A booking confirmed in between would be overwritten as `EXPIRED` and its seats released.

**Fix**:
- **One shared expiry.** The Checkout Session and the seat hold now expire at the same instant, so Stripe's own `checkout.session.expired` event is the normal way seats are released and the cron is only a fallback. Stripe requires a session to live at least 30 minutes; 31 minutes is used so the value is still valid when the request reaches Stripe.
- **Automatic refund as the safety net.** `confirmBooking` now returns the booking's resulting status. If a payment arrives for an `EXPIRED` or `CANCELLED` booking, the webhook refunds it in full (partner transfer reversed, platform fee returned), marks the payment `REFUNDED`, and creates no `PlatformTransfer`. Any other status (for example `CONFIRMED`) means an earlier delivery of the same event already did the work, and processing continues normally.
- **Conditional updates.** `expireBooking` and the cron only touch bookings that are still `PENDING`.

**Residual risk**: a payment completed in the last seconds of the window can still be delivered after the cron expired the booking. That case is exactly what the automatic refund covers.

## OI-3: A cancelled booking could still be paid, and a resumed one could be paid twice

**Where**: `bookings.service.ts`, `cancelBooking` (unpaid path) and `resumePayment`
**Severity**: High

**What the code did**: cancelling an unpaid booking only changed the database. Its Checkout Session stayed open for 24 hours. `resumePayment` created a second session and left the first one open as well.

**Scenarios**:
- A customer cancels, but a stale browser tab still shows the checkout page. They pay there. The booking is `CANCELLED` and the money has been taken.
- A customer resumes a payment, pays the new session, and later pays the old one from their browser history. They are charged twice.

**Fix**:
- **Cancel** updates the booking first, then closes the open session. If the customer pays in the gap, the webhook sees a `CANCELLED` booking and refunds it (OI-2).
- **Resume** creates the new session, saves it as the booking's current session and moves the seat hold, and only then closes the old one. If the old session turns out to have been paid in the meantime, the new one is discarded and the old one stays as the booking's session.
- **The webhook ignores a `checkout.session.expired` event about a session that is no longer current.** This is needed because closing the old session fires that event, and it must not expire the booking that was just resumed. It is also why the old session is closed after the new one is saved, and not before.
- A booking older than 2 hours cannot be resumed, so repeated resumes cannot hold seats indefinitely.

## OI-4: Partner authorization gap

**Where**: `partners/partners.controller.ts`, `startOnboarding` (`POST /partners/:id/onboarding`) and `getConnectStatus` (`GET /partners/:id/connect-status`)
**Severity**: High. In OWASP terms this is Broken Access Control (the top category of the OWASP Top 10).

**What the code did**: `@Roles(AppRole.ADMIN, AppRole.PARTNER_ADMIN)` decides which *roles* may call a route. It says nothing about *which partner* the caller may act on. Both routes took the partner id from the URL and trusted it.

**Scenario**: the partner admin of partner 1 calls `POST /partners/2/onboarding`. That generates a Stripe onboarding link for partner 2, and can create a Stripe Express account for them. `GET /partners/2/connect-status` returns partner 2's Stripe requirements and payout status.

**This is the same class of mistake as the role-metadata-without-a-guard bug in `AppController`**: authentication answers *who are you*, a role check answers *what kind of user are you*, and neither answers *is this particular resource yours*. That third question has to be asked explicitly.

**Fix**: `assertCanManagePartner(user, partnerId)`. An `ADMIN` may manage any partner. A `PARTNER_ADMIN` may manage only the partner matching their own `partnerId`. The check runs before the database lookup, so a foreign id and a nonexistent id both return 403, and ids cannot be discovered by comparing 403 with 404.

**Found during verification**: the first version of this check compared `user.partnerId` with the id from the URL using `!==`. At runtime `user.partnerId` is a `bigint` (it comes straight from Prisma's `BigInt` column, although `UserPayload` declares it as `number | null`), while the URL id is a `number`, and strict comparison across those types is always true. Every partner admin was therefore rejected, including the owner of the partner. The 403 cases of the test could not reveal this; only the control case (own partner should succeed) did. Both sides are now converted with `BigInt()` before comparing (see A8).

## OI-5: Personal and account data exposed in tour detail

**Where**: `tours/tours.service.ts`, `findOne` (`GET /tours/:id`)
**Severity**: High

**What PII means**: Personally Identifiable Information is data that identifies a specific person or lets someone contact or locate them: an email address, phone number, full name, address, ID number. Privacy law such as GDPR and Indonesia's Personal Data Protection Law (UU PDP, No. 27/2022) restricts how it may be collected and shared.

**What the code did**: the query used `include: { partner: true }` and selected `user: { id, email }` on every review and `createdByUser: { id, email }`. Any logged-in customer opening a tour page received:

| Exposed | Why it matters |
|:--|:--|
| Every reviewer's email | Emails can be harvested from tour pages for spam or phishing, and they are login identifiers |
| The tour creator's email | Internal staff contact details |
| The partner's `contactEmail` | Business contact details published to every customer |
| The partner's `stripeAccountId` | Not personal data in the strict sense, but payment-account data that should not be public |
| Flagged reviews | Reviews an admin moderated away were still returned |

**Fix**: the principle is *data minimization*: a response contains what the screen needs and nothing more. A review card needs a name and an avatar, not an email. The response is now shaped by role (the table is in `fixes.md`): customers and guides get only the partner's id and name, no creator, and unflagged reviews; admins and partner admins keep the management data they use; only admins see flagged reviews.

**Implementation notes**:
- `reviews.customerId` points at `auth.users` (which holds the email), not at `profiles`. The reviewer's first name and avatar are therefore read with one extra query for all reviewers of the tour, not one query per review.
- `is_flagged` is a nullable column, so "not flagged" has to match both `false` and `NULL`.
- The reviewer's first name and avatar are still personal data. A review is meant to show who wrote it, so that exposure is deliberate; the email was an accident of selecting the whole `user` relation.

## OI-6: Leftover review uniqueness constraint

**Where**: `prisma/schema.prisma`, model `Review`
**Severity**: Medium (it blocks a legitimate action, but loses no data)

**What the code did**: `@@unique([tourId, customerId])` was still declared. It enforces "a customer can review a given tour once, ever". The real rule is "one review per booking", enforced by `bookingId @unique`. The older constraint was not removed when the rule moved from per-tour to per-booking.

**Scenario**:

| | Booking | Old constraint | Intended behavior |
|:--|:--|:--|:--|
| Customer books Bali on Oct 5 | #10 | review allowed | review allowed |
| Same customer books Bali again on Dec 1 | #25 | second review rejected | review allowed |
| Customer reviews booking #10 a second time | #10 | rejected | rejected |

The customer would see "You already reviewed this booking", which is also the wrong message, because they had never reviewed booking #25.

**Why `id` does not do this job**: a primary key only guarantees that each row is distinct from other rows. Nothing about it prevents two reviews with different ids from pointing at the same booking. `bookingId @unique` says "this booking can have one review", which is the business rule. The compound constraint said "this customer can review this tour once", a different rule.

**Fix**: the constraint is dropped by the migration (`DROP INDEX "tour"."reviews_tour_id_customer_id_key"`). Lookups by tour or by customer stay fast because the separate `@@index([tourId])` and `@@index([customerId])` remain. Nothing in `src/` used the compound key (a search for `tourId_customerId` matched only generated files).

## OI-7: Platform transfer not reversed on refund

**Where**: `bookings.service.ts` (both refund paths), `prisma/schema.prisma` (`TransferStatus`)
**Severity**: Medium (financial records become wrong, no money is lost)

**What the code did**: a refund uses `reverse_transfer`, which takes the money back from the partner's connected Stripe account. The platform's own `platform_transfers` row for that booking still said `SUCCEEDED`. `TransferStatus` had only `PENDING`, `SUCCEEDED` and `FAILED`, and none of them describes "the transfer succeeded and was later reversed" (`FAILED` would be false).

**Scenario**: a report summing `SUCCEEDED` transfers per partner overstates what each partner actually received, by the amount of every refunded booking.

**Fix**: `REVERSED` is added to `TransferStatus`. Both refund paths set the booking's `SUCCEEDED` transfers to `REVERSED`: the API cancel path after the refund succeeds, and the `charge.refunded` webhook handler regardless of the booking's state. The update touches only `SUCCEEDED` rows, so it is idempotent. It never throws, because the refund and cancellation have already happened; and since the webhook repeats it, a failure in one path repairs itself.

**Migration note**: `ALTER TYPE ... ADD VALUE` is allowed inside a transaction on PostgreSQL 12 and later, as long as the new value is not used in the same transaction. The migration only adds it.

## OI-8: Webhook idempotency race

**Where**: `stripe-webhook.controller.ts` (event claim logic), `prisma/schema.prisma` (`StripeWebhookEvent`)
**Severity**: Low (it needs two concurrent deliveries of the same event)

**Background**: each Stripe event is claimed by inserting its id into `stripe_webhook_events` before processing. If processing fails, the claim is released and Stripe's retry processes the event again. That much was already correct.

**What the code did**: a claim was only a row, with no state. A duplicate delivery that found the row answered **200**, whether the first attempt had finished or was still running.

**Scenario**: Stripe delivers the same event twice almost at once (it can, for example when a retry overlaps a slow response). Delivery A claims the event and starts working. Delivery B arrives, finds the row, and answers 200, so Stripe treats the event as delivered and stops retrying. Delivery A then fails, releases its claim and answers 500, but Stripe already considers the event handled. The event is lost; if it was a payment confirmation, the booking never gets confirmed.

**Fix**: a nullable `completed_at` column gives the claim three states: claimed (row exists, `completed_at` empty), completed (`completed_at` set), released (row deleted after a failure).
- A duplicate of a **completed** event gets 200.
- A duplicate of an event **still in progress** gets **409**, which tells Stripe to retry later, after the first attempt has finished or been released.
- A claim that is neither completed nor released for more than 5 minutes (for example because the process crashed) is taken over by the next delivery.
- If marking an event completed fails, the claim simply goes stale and a later delivery reprocesses the event. The handlers tolerate that (transfer creation is guarded, status updates are conditional), and it is logged.

**Required in the migration**: existing rows must be backfilled with `completed_at = processed_at`. Without it they would look like abandoned claims and a redelivery of an old event could be reprocessed after 5 minutes.

## Decision rationale

**Why 31 minutes (OI-2).** Stripe only accepts a Checkout Session lifetime between 30 minutes and 24 hours. The old 15-minute seat hold therefore could not be matched by the session; the session would always outlive the hold by at least 15 minutes, leaving a window where payment is possible but the seats are gone. The alternative, keeping 15 minutes and closing every abandoned session through the API from the cron, needs a Stripe call per abandoned booking and still leaves the window open until the cron runs. Using one shared expiry removes the window. The extra minute is a safety margin, because Stripe validates the value when the request arrives, not when it is computed.

**Why refund automatically instead of re-confirming late payments (OI-2).** When a payment arrives after expiry, re-confirming is only possible if the seats are still free, and that needs extra logic (re-check availability, re-claim seats, handle the case where they are gone). A full refund is correct in every case and needs none of it. Re-confirming when seats remain is a possible later improvement.

**Why tour detail is shaped by role instead of simply removing the fields (OI-5).** The same endpoint feeds management screens (admin and partner dashboards) that legitimately need the partner record and the creator. Removing the fields would break them; returning them to everyone is the leak. Role-shaped output keeps both working.

**Why a 2-hour limit on resuming (OI-3).** Resuming moves the seat hold forward by a full payment window. Without a limit, calling resume every 30 minutes would hold seats forever. Two hours is a judgment call, not a requirement.

**Why 409 and not 200 for an in-progress duplicate (OI-8).** 200 tells Stripe the event is handled and ends retries. If the first attempt then fails, nothing will ever retry. 409 keeps the event alive until one attempt has actually finished.
